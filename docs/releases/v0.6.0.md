# TobiiLinux v0.6.0 — one list of games, and two screens that stopped giving bad advice

The hub's Games tab was four sections under four headings. It is one list now,
sorted by name, with the games that are set up drawn at full strength and the
rest drawn back — and a button beside the search box that shows only the set-up
ones.

The other half of this release is smaller and more embarrassing: two surfaces
were telling people to run a command that cannot reach their game, and both have
stopped.

Nothing in the driver, the protocol or the USB layer changed.

  Unofficial. Not affiliated with, endorsed by, or supported by Tobii.
  Use at your own risk.


## One list

The four sections were *Set up*, *Not set up*, *Set up, not installed here* and
*Added by hand*, and a row's section was decided by whether a profile file
existed for its app id.

That was the wrong question. No profiles ship with this program — `BUILTIN` is
empty — so a profile exists only where somebody wrote one with
`tobii games profile save`. On a fresh install the first section and the third
were both empty, which made the list one flat run of *Not set up* under four
headings, on every machine that had never used the feature.

What the tab is actually for is installing the Wine bridge, so that is what a
row is keyed on now. A row is lit when the bridge is in that game's prefix and
dimmed when it is not, and its second line says which — and tells apart the two
ways of not being set up, because they are different things to do about:
*no bridge yet* is something to press Install on, and *never launched* is a game
Proton has not made a prefix for yet. A game added by hand whose folder is not
on this machine right now says that instead: with the drive gone, this program
cannot see whether the bridge is in there at all.

The play triangle beside the search box narrows the list to the games that are
set up. It has no caption, because it is the same control Steam's own library
uses for the same question; resting a pointer on it says so, and so does the
help window. On a machine with one set-up game among thirty, that button is how
you find it.

Typing in the search box no longer rebuilds the list. It was torn down and built
again on every keystroke — 232 widget constructions and destructions on a
catalogue of 29 titles — and is now built once and narrowed, which is what the
help window has always done.

### The section that is gone rather than renamed

*Set up, not installed here* held profiles whose game Steam does not list on this
machine: an uninstalled title, or one on a drive that is not plugged in. Every
row in it opened a page with two of its three blocks replaced by a paragraph
saying the game is not here. It was a row whose purpose was to say it could not
be acted on.

The fact it carried was real, and it is not lost. A line under the list says how
many profiles here are for games Steam does not list, and names
`tobii games profile show` — which, with no app id after it, prints every profile
on the machine. The rows never named that command.

This is a trade and worth stating as one: a line under a list is less prominent
than a row in it. If you keep profiles for games you have uninstalled, that line
is now the only place the hub mentions them.


## Two screens that stopped giving bad advice

Both the hub and `tobii bridge install` told anyone who registered a third-party
TrackIR client that they must also run `tobii bridge run`. For a Steam game under
Proton that cannot work, and this project's own source has said so since the
receive loop moved into the client DLL: the game has its own wineserver, a
provider started from a terminal with system Wine is a different session, its
`FT_SharedMem` is a different object, and the game never sees it.

So the one user with no other route was being sent to run a command that could
not reach their game, and then left to conclude the bridge was broken when it did
not help.

Both now say what is actually true: our own DLL fills the mapping from inside the
game's own process, replacing it with somebody else's takes that away, and
whether anything else in the game's session would fill it is not something this
project has watched. `tobii bridge install` still prints the command for a prefix
Proton does not serve, where it does work — with the path quoted, which it was
not, so a Steam library folder with a space in it pasted back as four arguments.


## Smaller things

- The hub had its own copy of the shell quoter, making four in the workspace, and
  the copies disagreed: the same path printed `'/opt/x'` in the hub and `/opt/x`
  in `tobii uninstall`. There is one now, and a path needing no quotes is left
  alone.
- `tobii bridge install` and the hub spelled the two discovery registry keys
  separately, with nothing tying them together. A test now asserts they are the
  same two paths.
- The Games help topic read "Uninstall takes it back out, and and the last
  runs…", and named that button by its position after it had been renamed.
- `setup_line` took an `Option<bool>` in which `Some(false)` meant "nothing
  saved" and `None` meant "unreadable". It takes a named type now, and the caller
  no longer folds a config file it could not read into "no display set up yet".


## Under it

`Catalog::new` used to take two closures so that the three `is_file` calls behind
*bridge installed* were paid only for rows with a profile, and the test fixture
passed a closure that panicked if that promise was broken. The promise is gone
deliberately, so the guard went with it; what replaced it asserts the half that
can still rot silently — exactly once per row, never twice. The cost is unchanged
prefix walks plus three stats per row that has a prefix at all, once per visit to
the tab.

The prefix memo in `Scan` turned out to have a 0% hit rate: the two closures were
mutually exclusive, so every app id was asked once, inserted once, and cleared
before the next read. It is gone.

`tests/games_filter.rs` is new. It is the only test that can reach the two GTK
facts the rewrite rests on — that a filtered-out row is still found by
`row_at_index`, and that the paragraph explaining an empty list appears when the
filter is what emptied it. The second is why the list no longer uses
`GtkListBox::set_placeholder`: GTK parents that widget somewhere no test outside
the crate can reach, and a window that prints a paragraph explaining why it looks
empty should not rest on a claim about a toolkit that nothing here can check.

1522 tests pass, 18 ignored, none failing. Nine of the ignored ones need a
display — eight of those are whole-hub integration tests that
`scripts/display-tests.sh` runs by hand — seven need the 13 MB head-pose model,
one needs write access to `/dev/uinput`, and one needs wine and two Windows
stubs.
