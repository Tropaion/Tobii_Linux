# TobiiLinux v0.7.0 — the launch carries the bridge

Head tracking for a Steam game under Proton needed something filling a shared
mapping inside the game's own Wine session, and starting that by hand was the
problem: anything of ours alive on the prefix when Steam launches does not delay
the launch, it prevents it. This release stops being in that race.

Put this in a game's Steam launch options:

```
tobii game -- %command%
```

and Proton starts our provider and the game together, in one invocation, after
its own lock is taken. The provider ends when the game does. Nothing to start
first, nothing to restart, nothing left running.

  Unofficial. Not affiliated with, endorsed by, or supported by Tobii.
  Use at your own risk.


## What changed, and why this shape

Steam launches a Proton title with the verb `waitforexitandrun`, and Proton runs
`wineserver -w` — a wait for every Wine process on the prefix — **before** it
spawns the game. So `tobii bridge run` started beforehand leaves the launch
sitting there, and v0.5.0 made it stand down instead, which unblocks the launch
and delivers nothing.

The way out is not to win that race but never to be in it. Steam hands the
wrapper the whole command it meant to run. `tobii game` now points Proton at
**our provider**, with the game after `--launch`: one `waitforexitandrun`, one
`wineserver -w`, and both processes born after the lock, in the session the game
is in.

The shape came from [markx86/opentrack-launcher], which a user found and which
is what showed this project that the session can be *joined* rather than
recreated. The mechanism was read; no code, binary or file of it is used here.
That launcher substitutes a batch file, and this project did too until it was
measured: Proton's `steam.exe` runs an `.exe` target through `CreateProcessW`
and waits, and a `.bat` through `ShellExecuteW`, which returns at once. Pointing
Proton at a batch has Steam record the game as exited a second in — survivable
for a launcher whose only job is to start and reap another program, not for
`tobii game`, which releases the tracker when it returns. So the target is the
provider itself, which is already in the prefix and is an `.exe`.

[markx86/opentrack-launcher]: https://github.com/markx86/opentrack-launcher

Three things follow from the target being an executable rather than a script:

- **Steam's bookkeeping stays right.** Playtime, the Stop button and the overlay
  see a process that ends when the game does.
- **The reap is process exit.** No `taskkill` to be skipped by a signal, and no
  surviving helper to block the *next* launch's `wineserver -w`.
- **The command line is argv.** A batch file cannot carry a quote, a control
  character or anything non-ASCII — all measured — so a game under a path with
  an umlaut in it could not be wrapped at all. That restriction is gone, and the
  game's path is no longer rewritten even to a Windows spelling: Proton's own
  `protonfixes` layer matches on the spelling Steam produced, and converting it
  here would have silently cost a fixup on every wrapped launch.

The hub does the rest of it. The Games tab's Install button puts the bridge in
the prefix, *Install another client…* points TrackIR at opentrack's client for a
title measured to refuse ours, and game output is a switch on the Tracker tab.
The launch option is the one step that is not a button, so the page names it and
offers to put it on the clipboard — over a prefix whose bridge can start a game,
and over one installed before v0.7.0 it says that instead and names Reinstall — this program does not set it, because launch
options live in Steam's own configuration, which Steam rewrites from memory when
it exits, and writing another program's files is the rule the game-settings block
is built on.

It declines, and says so, rather than guessing: when the command is not a Proton
launch, when `STEAM_COMPAT_DATA_PATH` does not say which prefix it uses, when
the prefix has no bridge, and when the bridge predates this feature — run
`tobii bridge install` again for that game. Every declined command is run
exactly as Steam wrote it.


## Measured, and not

Against real Proton — `proton-cachyos-slr`, a scratch prefix, no Steam install
touched: Proton returns the game's exit code after the full run; ASCII arguments
arrive byte-identical; the provider's mapping and UDP port come up in the host's
own network namespace, which is what lets a datagram from Linux reach it; and
nothing outlives the run. `crates/tobii-cli/src/proton.rs`'s end-to-end test
reproduces the argument fidelity, the exit code and the reap under wine.

**Not measured: that a given game then reads the mapping.** For a title that
checks NaturalPoint's signature our own client is refused — MSFS 2024 calls that
check 104 times in 1m45s and nothing else — so the configuration that could work
is a third-party client answering the check with our provider filling the mapping
behind it. Those are two conditions and this project has measured them
separately, never together. Also unmeasured: Steam's own bookkeeping (Proton was
invoked directly), the Steam runtime container, and any Proton build but one.
`docs/wiki/Quality-and-Risks.md` §11.3o has the full list.


## The Wine bridge could not be built from v0.6.0

`tobii-config` grew a module using `std::os::unix::ffi::OsStrExt`; `tobii-output`
depends on that crate and the bridge depends on `tobii-output` and
cross-compiles to Windows. So `scripts/build-bridge.sh` failed on a clean
checkout of the tag, with four errors, while every check stayed green — nothing
anywhere compiled the bridge. The module is Linux-only now, and **CI builds the
bridge**, which is the part that matters. Release artifacts were unaffected:
they have never contained the bridge.


## Also

- The Games tab's census had no guard at all: which count `rebuild` draws was a
  choice nothing checked, so `cat.rows.len()` in place of `cat.installed` would
  have passed every test. The display test reads the label now, over a fixture
  where the two numbers differ, and the substitution was mutation-tested.
- `tobii bridge install` told the one user with no other route that nothing of
  ours could fill the mapping under Proton. It names the launch option instead.
- The client DLL could cede the UDP port permanently to a provider that had
  since exited, leaving a game reading a mapping with no writer — a head frozen
  at its last pose. Ceding no longer ends the watch.

1512 tests pass and 18 are ignored, none failing in the run this was cut from.
Nine of the ignored need a display, eight of those being whole-hub integration
tests `scripts/display-tests.sh` runs by hand; the rest need the head-pose
model, `/dev/uinput`, or wine and a stub game.
