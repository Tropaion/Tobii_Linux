# TobiiLinux v0.4.1 — the tracker stays on for a game, and the bridge stops overwriting other programs

A fix release. One issue was reported against v0.4.0 and it turned out to be the
larger of two holes in the same idea; both are fixed here, along with a
destructive bug in `tobii bridge install` that nobody had hit yet.

No driver, protocol or USB behaviour changed.

  Unofficial. Not affiliated with, endorsed by, or supported by Tobii.
  Use at your own risk.


## The tracker went dark a few seconds after you looked at your game

Reported as "as soon as I swap to another window, after 3 to 5 seconds, the
tracker goes off and nothing is sent to the joystick". It did, and the report
was right that it was our bug rather than a setting.

The hub keeps the infrared illuminators dark unless something is asking for the
tracker. Three things could ask: the hub's own window while it has focus, a
program connected to the hub's socket, and — since v0.4.0 — a program bound to
the opentrack address. The virtual joystick could ask for nothing at all, and it
is the only sink that is on by default, because it is the only one that works on
a machine with nothing else installed. So the out-of-the-box configuration was
exactly the one the design could not serve. The "3 to 5 seconds" is a fixed
three-second wait before the USB session closes; measured here at 3.00 s.

Two settings fix it, both in `games.toml`:

    tobii games set wake_for_joystick true    # on by default
    tobii games set keep_awake true           # off by default

`wake_for_joystick` makes the switch itself the request: while game output is on
and the joystick device actually exists, the hub holds the tracker. There is
nothing narrower to ask, and that is not a guess — detecting whether a game has
the joystick open was tried and rejected on measurement. A faithful replica of
our device was opened by three unrelated processes within 30 milliseconds of
being created, with nothing reading it, and never had zero openers again for the
life of a Wine prefix. A signal that is always true is not a signal.

`keep_awake` is the fallback for everything that cannot be detected: a
Wine-bridge-only setup whose listener is a DLL inside the prefix, an opentrack on
another machine, a launcher that will not pass a command through. It switches
standby off outright.

Both weaken standby, in one direction and honestly: `wake_for_opentrack`'s hold
ends when opentrack exits, but these end only when you remember. That is why the
hub shows an ALWAYS ON badge in its header while `keep_awake` is set, rather
than leaving it behind a cogwheel.


## `tobii headpose` could not run while the hub was open

A consequence of the above, found in review rather than by use. With the hub
holding the tracker permanently, `tobii headpose` — which opened the USB device
directly — failed with "already claimed by another process" for exactly the
people the fix above was for. That includes `--calibrate-pitch`, which is the
documented way to fix a pitch that reads wrong.

It now asks the hub to stand down first. The hub answers one of three ways: it
lets go and says so, it refuses because it is mid-calibration or mid-display
setup, or it is not running at all and the command opens the device directly as
it always did. The tracker is handed back explicitly when the command ends.

The mechanism for this had been in the hub since v0.2.0 and nothing had ever
used it.


## `tobii bridge install` overwrote other programs' registrations

A Wine prefix records which head-tracking client a game should load. `install`
wrote that key without reading it, and `uninstall` deleted it rather than
putting anything back — so installing over a working opentrack registration
destroyed it silently, and uninstalling afterwards left the prefix with no
client at all, which is worse than before the command ran.

It now reads first. A key holding another program's registration stops the
install, with the value named and `--force` offered; a key it did not write is
left exactly as it is on uninstall, with the reason given. The record it keeps
holds only what this program itself wrote: a value read from the registry is
compared and dropped, never stored and never written back. That is a property
rather than a promise — there is no code path that can write a value it did not
compute, so a value it misreads cannot be written anywhere.

This took five rounds of review over six commits to get right. Two of them
produced fixes that recreated the fault they were written to prevent, which is
why the restore feature is gone rather than repaired: a design that cannot
express the failure beat one that kept being patched out of it.


## `tobii bridge install --help` performed an install

Unrecognised flags were ignored, so the first thing anyone types at an
unfamiliar command ran a real install into the default Wine prefix and said
nothing about the flag. Any flag a subcommand does not read now stops the
command before it resolves, creates or writes anything.


## Smaller things, all from the same report

- The eye-position panel said "not detected" whether the tracker was off on
  purpose or genuinely failing. It now says "tracker off" for the first.
- `tobii debug` has a "game output" section: the sinks, the wake settings, and a
  "can wake it now" line that either names what is allowed to light the tracker
  or says NOTHING and what to turn on. That one line is what would have answered
  the original report from a single paste.
- The hub logged "game output on" every time a session opened and never said
  anything when one closed.
- The games card no longer promises a hold that the settings have turned off.


## Known limitations

- None of this has been run against a tracker by anyone but its author.
- No long soak: nobody has left a tracker lit for eight hours, which
  `keep_awake` and `wake_for_joystick` now make easy to do by accident.
- The joystick hold is per-setting, not per-game: with game output on, the
  tracker stays lit whether or not a game is running. The wrapper
  (`tobii game -- <command>`) remains the tighter hold, because it ends when the
  game does.
- `tobii bridge install`'s refusal has been exercised against a real Wine
  prefix and a scripted one, but not against a Proton prefix belonging to a
  game that was running at the time.

Three interactions between the new permanent holds and the lease are known and
are not fixed here. A pitch calibration holds the device for about thirteen
seconds without declaring itself, so a `tobii headpose` started inside that
window is told the hub did not answer and then fails the old way. A command
queued in the hub while `tobii headpose` holds the lease waits instead of
failing, so the pitch-zero dialog sits on "starting in 3 seconds" with no
explanation until the command ends. And while the hub has stood down it keeps
its virtual joystick device, so `tobii headpose`'s own joystick sink is
suppressed and a game bound to the hub's controller sees its axes frozen —
opentrack and the Wine bridge still carry the pose.

docs/wiki/Quality-and-Risks.md §11.3f and §11.3g have these in full, with what
was measured and what was not.


## Upgrading

`tobii update` replaces the two binaries. Your settings and calibration are
untouched, and the two new keys take their defaults, so a hub that was sending
to a game will now keep the tracker on where it used to go dark. If you would
rather it did not, `tobii games set wake_for_joystick false` restores exactly
the old behaviour.
