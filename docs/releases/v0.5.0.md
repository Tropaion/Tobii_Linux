# TobiiLinux v0.5.0 — help you can search, and a bridge that stops damaging prefixes

Two things arrive: a help window the hub never had, and a way to ask a Wine
prefix what is in it without changing it. Most of the rest of this release is
the Wine bridge learning not to break things it was never meant to touch.

Nothing in the driver, the protocol or the USB layer changed.

  Unofficial. Not affiliated with, endorsed by, or supported by Tobii.
  Use at your own risk.


## Press F1

The hub's cards used to explain themselves in a paragraph each. Those
paragraphs are now shorter, or gone, and what they said lives in a help window:
nine topics, a list to move between them, and a search box that reads headings
and bodies both. It opens on the search box, because you usually arrive with a
word off the control in front of you rather than with a heading in mind. Escape
or F1 closes it; there is a "?" in the header and a row in the cogwheel for the
mouse.

It is also where things that were only ever tooltips now live. A tooltip cannot
be reached by keyboard or by touch — GTK4 has no way to raise one — so every
fact a card states only in a tooltip is in the help window too, quoted from the
same string rather than copied, with a test that fails if the two ever drift.

One card description was deleted rather than moved: "Shows you a visual trail
of your gaze" was never true. The overlay draws one circle at the point you are
looking at, and has since it was written.

The six card descriptions were 215px of wrapped text between them; three were
shortened and two removed. Measured end to end on the real hub: the window's
natural height was 748px before and is 692px after, at an unchanged natural
width of 1241px. (That pair was recorded as being at text scale 1.0 and was
not — the machine it was taken on has a saved scale of 1.2, which `load_css`
applies. At a pinned 1.0 the width is 1189px. The *difference* is the fact;
the absolute numbers were somebody's settings.), and the six cards went from 180/161/141/213/120/204 to
142/142/96/194/94/204. So the window opens 56px shorter and every card that
gave up prose is shorter with it.


## Ask a prefix what is in it

    tobii bridge status --steam <app id or name>

What is installed in that Wine prefix, what each of the two head-tracking
discovery keys holds, whether that value is ours or somebody else's, and
whether a wineserver is alive on the prefix. Short enough to paste into an
issue, which is what it is for.

It starts no process at all. That is the whole design: it reads the prefix's
own user.reg rather than asking wine, because running wine against a prefix
initialises or upgrades it. The first version of this command did ask wine, and
a review measured what that cost — 5510 files created in a prefix that had
never been booted, and 2744 lines of system.reg rewritten in one shaped like a
Proton prefix. A command you run to find out what is wrong must not change what
is wrong.

Reading the file instead has one honest cost: a live wineserver holds changes
in memory, so the file can lag. The report says so when that is the case.


## The bridge stops taking what is not its

`tobii bridge install` used to write the two discovery keys without reading
them, and `uninstall` deleted them rather than putting anything back. Installing
over a working opentrack setup destroyed it silently.

Now: install reads first and refuses when a key holds something it did not
write, naming the value and offering `--force`. Uninstall removes a key's value
only while it still matches what install recorded writing, and leaves anything
else alone, saying which and why. One limit is worth stating rather than
implying: a value that is byte-for-byte what this installer would have written,
with nothing recorded either way, counts as ours — a value-equality test cannot
tell our own registration from another program's at the same path. That is what
lets an install made by an older version be taken back out, and it is the
reason `tobii bridge status` exists to show you what is actually there. The
record holds only values this program computed itself, so a value read from the
registry is compared and dropped, never stored and never written back. That is
a property rather than a promise: there is no path that can write a value it
misread.

While nothing is serving the prefix, a refusal costs the prefix nothing at all:
it reads the file, decides, and never starts wine. With a wineserver alive the
file can lag, so the decision goes through wine instead.

Two more things that could damage a prefix:

`tobii bridge install --steam` now refuses when it cannot tell which wine the
prefix belongs to. A Steam prefix was made by a Proton build, so the host's wine
is by construction the wrong one, and using it runs `wineboot -u` against a
prefix it does not own. `--wine` names the right one; `--force` proceeds anyway.

`tobii bridge install /games/pfx` used to drop the typed path and install into
`$WINEPREFIX` or `~/.wine` instead, saying so nowhere. A bare path is now
refused by the same gate that has refused unknown flags since v0.4.1, before
anything is resolved, created or written — the fifth hole found in that one
gate.


## `tobii bridge run` gets out of the way

Running it used to hang the next launch of the game. Not because the game
objected: Steam starts a Proton title with `waitforexitandrun`, and Proton runs
`wineserver -w` first, which waits for every wine process on that prefix to
exit. The bridge was one. Measured here, a `wineserver -w` sat for the full
timeout with one process holding the prefix and returned the instant it died.

It now says so before it takes that lock, and stands down by itself when it
sees a launch waiting, so the launch goes through. Start it again once the game
is up — a client picks up tracking that appears late. That only unblocks the
launch: whether a bridge started outside the game's container joins the game's
own wineserver is unconfirmed, and if it does not, the game still sees nothing
from `bridge run`.

The Windows-side provider also stopped rewriting both discovery keys every time
it starts, which could take the TrackIR registration off the third-party client
that is the only reason a TrackIR game works at all.


## Known limitations

- None of this has been run against a tracker by anyone but its author.
- Whether any game accepts our own TrackIR client is unmeasured. The only
  title ever put to that test is Star Citizen, which rejected it in August. If
  you are trying to get head tracking into a TrackIR game, that is the open
  question, and `--npclient ours` is the way to find out.
- The bridge's refusal and uninstall rules have never met a real third-party
  registration through a whole cycle, nor a Proton prefix belonging to a game
  that was running at the time.
- Reading user.reg is a second implementation of wine's own reader. Seven
  disagreements between the two have been found and fixed by review; there may
  be more.
- `tobii bridge run` installs no signal handler, so a kill aimed at the `tobii`
  process alone orphans the wine child that holds the prefix lock.
- CI has no display, so the five tests that need one are skipped there. They are
  run by hand before a release.

docs/wiki/Quality-and-Risks.md sections 11.3h, 11.3i and 11.3j say what was
measured and what was not.


## Upgrading

`tobii update` replaces the two binaries. Settings and calibration are
untouched, and nothing in this release changes how the tracker behaves for a
game — the standby changes were in v0.4.1.

If you have installed the Wine bridge into a prefix with an older version, it
is worth running `tobii bridge status` on it: older versions wrote the registry
without reading it, so a key may hold ours where it used to hold something
else, and the report will say so.
