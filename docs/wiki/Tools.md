# Tools

Three binaries are built from this tree, and two of them ship in a release: the
`tobii` CLI (`crates/tobii-cli`) for talking to live hardware, and the
`tobii-gtk` hub (`crates/tobii-gtk`). `tobii-recap` (`crates/tobii-recap`)
decodes a captured USB trace offline; it is a development tool and is not in
the release archive.

## `tobii` CLI

Source: `crates/tobii-cli/src/main.rs`. All device-touching commands open the
ET5, run the handshake, and — where gaze data is needed — re-apply the saved
display area first (the device wipes it on reboot; see [[Display-Area]]).

| Subcommand | Purpose |
|-----------|---------|
| `tobii debug [--file PATH]` | Print everything an issue report needs and nothing that identifies you, **including the tail of the log**: versions, the distro/kernel/glibc, session type, library versions, whether the tracker is on the bus (read from sysfs — it never claims the device, so it works while the hub is running), whether the udev rule is installed, and what is configured. **No calibration data**; the monitor id is hashed because it is derived from the EDID serial; the home path, username and hostname are left out. Since v0.4.1 it also carries a **game output** section — `enabled`, `sinks`, `wake settings` (each with the fact that makes it effective: whether anything is actually bound at the opentrack address, probed with the same `listener::probe` the hub's watch uses) and `can wake it now`, which names every path that could light the tracker at that moment or prints `NOTHING` and what to turn on. That line is what issue #2 needed and could not produce. Small enough to paste, which matters: GitHub issue forms can require a pasted field but have no file-upload field at all. |
| `tobii record [--calibration] [FILE] [FRAMES]` | Record a real session — handshake, display-area apply, eye selection, gaze subscribe, N gaze frames, unsubscribe — to a replayable capture. Writes `crates/tobii-usb/tests/captures/session.tobiicap` by default. The capture is line-oriented hex with a header carrying when it was taken and the display geometry used, so `cargo test -p tobii-usb --test replay` reproduces the same frames on a machine with no tracker. Re-record after a firmware update: a capture is a photograph of one session, not a specification. |
| `tobii update [--install]` | Check GitHub for a newer release and print its changelog. `--install` downloads the archive for this machine, checks it against the release's `SHA256SUMS`, runs the new binaries once to confirm they work here, and then replaces the installed ones — rolling every one of them back if any step fails. The checksums are published in the same release as the archive, so they catch a corrupted download, not a hostile one; see [Updates](../../README.md#updates). |
| `tobii uninstall [--dry-run] [--yes] [--purge] [--udev] [--system] [--bindir DIR]` | Take the program back off this machine. It finds the install locations by inference — the menu entry's and the autostart entry's `Exec`, and where this binary itself runs from — identifies each candidate binary by what it prints for `--version`, and says that is what it did rather than claiming it verified them. `--dry-run` prints the whole plan and changes nothing; it names what it keeps and what it is not doing, so the report can be read before the destructive run. |
| `tobii stream [--json] [--eyes]` | Connect and print decoded gaze samples (timestamp, `gaze_point_2d`, validities). `--eyes` also prints trackbox + eye-origin geometry; `--json` emits one JSON object per frame. |
| `tobii bridge games` | List Steam libraries and installed games, marking which have a Proton prefix. |
| `tobii bridge install --steam <app id or name>` | Install the Wine-side DLLs into a Steam game's Proton prefix, resolved from Steam's own library files, and write the registry with **the Proton build that prefix records** (a foreign wine would upgrade the prefix). `--prefix PATH` for anything not Steam. Nothing has to be left running afterwards — the DLL receives tracking itself. **It can refuse:** the two head-tracking discovery keys belong to whoever registered in that prefix first, so a key holding something this installer did not write stops the install with the key, its value and the `reg delete` line to clear it by hand. `--force` registers ours anyway and promises nothing about putting the old value back — only the values this installer wrote are recorded, so there is nothing of anyone else's to restore. **Since v0.5.0 `install` can also refuse over the wine itself:** a `--steam` prefix was made by a Proton build by construction, so if which build cannot be read out of the prefix and the only candidate left is the host's `wine`, the install stops rather than run it — that wine would `wineboot -u` the game's prefix before writing anything. Name the build with `--wine <Proton>/files/bin/wine`, or pass `--force` to go ahead knowing it will upgrade the prefix first. `run` and `uninstall` warn about the same wine and go on. Since v0.4.1 every `tobii bridge` subcommand also **refuses a flag it does not read** — including `-h`, `--prefix=PATH` and a `--prefix` with nothing after it — before it resolves, creates or writes anything: an unknown flag used to be ignored, and `tobii bridge install --help` performed a real install into the default prefix. A **bare positional** is refused with them: `tobii bridge install /games/pfx` used to drop the path and install into `$WINEPREFIX` or `~/.wine` instead. The refusal itself starts no wine either **while the prefix's wineserver lock is free** — it reads the prefix's own `user.reg`, as `status` does, and wine runs only once the command has decided to write, so a prefix that is refused comes out byte for byte as it went in. With a wineserver alive the file can lag behind the registry, so the decision is taken through `wine` and a refusal does touch the prefix; that is deliberate, because a stale read of an empty key would let the install overwrite the very registration the refusal protects. See [[Game-Output]]. |
| `tobii bridge status --steam <app id or name>` | **Read-only.** What is in a prefix right now, in a block short enough to paste into an issue: which prefix was resolved and how, which `wine` and whether the prefix itself corroborates it, which of the three artifacts are in `drive_c/tobii-bridge`, what each of the two discovery keys holds — and whether that value is this installer's, a third party's, absent or unreadable, decided by exactly the rules `install` and `uninstall` act on — and whether a wineserver is serving the prefix. `--prefix PATH` for anything not Steam. It **starts no process at all** — it reads the prefix's own `user.reg`, the install directory and this installer's note of what it registered, and probes the wineserver lock with `F_GETLK`, which takes nothing. Running `wine` would have been the change: wine initialises or upgrades whatever prefix it is pointed at, and a command run to find out what is wrong must not change what is wrong. Because `user.reg` is the registry as last written back, the report says so when a wineserver is alive and the file may therefore lag. It names paths unredacted, unlike `tobii debug`. It reports **what is registered, never what a game will do with it** — the only title ever measured against NaturalPoint's signature check is Star Citizen, so no line in it says "ready". See [[Game-Output]]. |
| `tobii bridge uninstall --prefix PATH` | Take out what the install put in. An uninstall with nothing of ours to remove starts no wine either, for the same reason `status` does not — and with the same condition: while a wineserver is alive on the prefix the check goes through `wine`, because `user.reg` can lag. It removes a discovery key's `Path` only while that key still holds this installer's own directory or exactly the value the record says this installer wrote; anything else is left as it is and named. Then the install directory goes, and only once the registry came out right. |
| `tobii bridge run --prefix PATH` | Optional. A console showing what arrives and what is rejected — and the one thing still *required* when TrackIR is pointed at a third-party client DLL, which is a pure consumer of the shared memory our own DLLs create. **Start the game first**: while this runs it is a wineserver on that prefix, and Steam waits for every wineserver on a prefix to exit before it spawns the game. It warns about that before it starts, and stops itself if a launch starts waiting behind it — see [[Game-Output]]. |
| `tobii game -- <command>` | Run a command with the hub's tracker held on for its lifetime. It carries **no tracking data**: it connects to the hub's socket, subscribes to pose, and drops the subscription when the child exits, which is what makes the hub light the tracker while a game runs (`outputs::Holds::hello`). Needed for the hub's route to the **Wine bridge**, which is the one sink with nothing to see: for opentrack the hub sees the receiver's own socket (`wake_for_opentrack`), for the virtual joystick the switch itself holds the tracker since v0.4.1 (`wake_for_joystick`), and `tobii headpose` opens the device itself. Still the most precise of the lot — it holds the tracker for the child's lifetime and not a second longer, where the two settings hold it until a human turns them off. Transparent to the launcher: the child's exit code, 128 + signal for a kill, and never a refusal to start. See [[Game-Output]]. |
| `tobii games` | Print the game-output settings and the path of the file they live in. |
| `tobii games set KEY VALUE` | Change one setting. Writes through the same `apply_key` the file parser uses, so the CLI cannot accept a spelling the file would reject. `enabled`, `rate_hz`, `filter_alpha` and `filter_max_step_mm` (the pose filter's smoothing and its jump limit), `opentrack`, `wake_for_opentrack` (the opentrack-port watch), `bridge_port`, `joystick` and its full-swing angles, `wake_for_joystick` (default **on**: the virtual joystick existing is itself a request for the tracker, for as long as game output is on — there is nothing narrower to ask, see [[Game-Output]]), `keep_awake` (default **off**), plus the Extended View tuning — `tobii games` prints the file with every key in it, and a rejected key prints the full list. `keep_awake` is a **standby** setting rather than a game-output one: it switches standby off outright, holding the tracker for as long as the hub runs, with game output off and with no sink configured. It lives in `games.toml` — and is reached as `tobii games set keep_awake true` — only because that is the file the hub re-reads once a second, so a change takes effect while you are watching the tracker rather than at the next restart; the hub's cogwheel sets the same bit as **Keep the tracker awake**. See [[Game-Output]]. |
| `tobii headpose [--udp ADDR] [--rate HZ] [--model auto\|off\|FILE] [--check [--calibrate-pitch [SECS]]] [--extended-view\|--no-extended-view] [--recenter]` | Stream head pose to opentrack over UDP (default `127.0.0.1:4242`, 60 Hz). A **complete route on its own**: it opens the tracker, and anything that binds that port — opentrack's UDP input, X-Plane's `headtrack` plugin — receives it with no hub and no `tobii game`. Where a hub *is* running it asks for the tracker first and says so (`the hub has let go of the tracker for this run`), giving it back when the command ends; a hub that refuses — mid-calibration, mid-display-setup, or already lent out — fails the command with its own sentence, and which sentence depends on which refused: mid-calibration and mid-display-setup give `the hub is busy with …`, which lists every reason the hub is holding and not only the flow that refused (so it can name `standby turned off in the settings` beside the calibration); a tracker already lent to another client gives `the tracker is leased by <that client's name>`, which lists nothing else. With a model installed this is **6 DOF** — position from the eye origins, rotation from the neural model; without one it is the 5-DOF geometry and **pitch is 0**. Sinks beyond opentrack — the Wine bridge port, the virtual joystick, Extended View — are added only when `games.toml` has `enabled = true` (or `--extended-view` for the one run), so a bare invocation is what it always was: head pose to opentrack. `--check` prints the model's yaw/roll beside the geometry's, which is the experiment that settles the sign conventions. `--recenter` (`--recentre` too) takes a rotation reference at the start of the run. See [[Head-Pose]]. |
| `tobii headpose --model-status` | Report which head-pose models are installed in `~/.config/tobii-linux/models` and whether their sha256 matches the pinned one. |
| `tobii headpose --fetch-model [--agree]` | Show the model's licence terms, ask for explicit consent, then download + verify + install it. `--agree` answers the prompt (for scripts); nothing is fetched without one or the other. Same flow as the GUI's **Head tracking** section. |
| `tobii headpose --check-update` | Ask whether a newer head-pose model has been published, without downloading one. |
| `tobii headpose --remove-model` | Delete the installed head-pose model, returning `tobii headpose` to the 5-DOF geometry. |
| `tobii headpose --install-model <FILE>` | Install a model you already have. Refused unless its sha256 is the pinned one — a different file is worse than none, because its output looks plausible. |
| `tobii columns` | Diagnostic: stream the FULL column inventory of each gaze frame (~2 Hz), including columns `stream`/`headpose` discard. Move your head one axis at a time to see which columns track motion. Flags unmapped columns. Needs a valid display area. |
| `tobii probe-streams [START] [END]` | Hunt for undiscovered streams: baseline gaze-only notify ops, subscribe across `START..=END` (default `0x501..=0x520`), report which notify ops newly appear. See [[Streams]]. |
| `tobii probe-stream <ID_hex> [SECS]` | Deep-dive on ONE stream: subscribe, read `SECS` (default 5), report rate, payload size range, whether the payload changes frame-to-frame (live vs static), and a hex preview. |
| `tobii streams` | Ask the device for its OWN stream catalog (`0x4b0`) and print every stream id it advertises, with names. See [[Streams]]. |
| `tobii log [SECS]` | Subscribe to the device's ASCII log stream (`0x1772`) and print it for `SECS` (default 30). The firmware's own view of what it is doing. |
| `tobii dump-stream <ID_hex> [COUNT]` | Dump `COUNT` (default 3) raw payloads of one stream to files in a fresh private directory. |
| `tobii camera [ID] [COUNT]` | Capture camera frames from one image stream (default `0x501`) and write them as PGM. |
| `tobii camera both [SECS]` | Capture `0x501` and `0x50e` together for `SECS` (default 6), pair them by timestamp, and report whether the two cameras differ. On this ET5 they are byte-identical, on a face and on an empty scene alike — `0x50e` is the **same** camera as `0x501`, not a second view. |
| `tobii cal-blob` | Retrieve the stored calibration (`0x44c`) and report its size, the 2-byte status prefix, and a preview — the quickest way to tell a real blob from a stub. See [[Calibration]]. |
| `tobii cal-points` | Ask the device for its own stimulus point set (`0x460`) and decode the reply. |
| `tobii setup` | Interactive display-geometry wizard: detect the monitor, prompt for width/height/tilt/offsets/curvature, compute corners, save config, and apply to the device. |
| `tobii display get` | Read the device's current display area (`0x596`), print the three corners and the derived setup. |
| `tobii display set` | Apply the saved config's corners to the device (`0x5a0`). |
| `tobii calibrate [--apply]` | Run a **headless** 5-point calibration (no dots drawn — validates the protocol, not accuracy), compute+apply, and retrieve the blob to report whether its size changed. **Nothing is saved** — no stimulus is drawn, so the points are positions nobody looked at, the result cannot be a usable calibration, and the command says so before it starts and again when it ends. `--apply` re-applies the blob the GTK flow saved. For accurate calibration use the GTK follow-the-dot flow. |
| `tobii cal-probe` | Non-destructive calibration-session probe: `start` then `stop` only (no `clear`, no `compute`), to check the device still accepts these ops. |
| `tobii enabled-eye [both\|left\|right]` | Get (and optionally set) "Select eyes to detect" (`0xc62`/`0xc58`). See [[Select-Eyes]]. |

The GUI (`crates/tobii-gtk`) provides the follow-the-dot calibration flow
(seven points, shown in three groups), the display-setup UI, and an
eye-position/gaze overlay.

## `tobii-recap` — pcap → TTP op catalog

Source: `crates/tobii-recap/`. Decodes a **usbmon pcap** capture of ET5 traffic
into a human-readable TTP timeline and op catalog — the offline counterpart to
the live probes, and the tool used to analyze a Windows-VM capture of Tobii's own
software.

```
tobii-recap <capture.pcap> [--limit N] [--gaze-columns]
  --limit N          cap the number of timeline lines printed
  --gaze-columns     dump the column inventory of each gaze notify (0x500)
```

It reassembles TTP frames from the usbmon URBs, labels each with its magic
(REQ/RSP/NOTIFY), direction, and op name (via the shared `opnames` table —
`op_label` prints `?unknown` for unmapped ops, which are exactly the
reverse-engineering targets), and can expand gaze frames into their column
inventory using the same `tobii-protocol::gaze::column_inventory` the live tools
use. **[CONFIRMED]** — `tobii-recap/src/main.rs`, `opnames.rs`. Modules:
`pcap.rs`/`usbmon.rs` (capture parsing), `decode.rs` (framing), `catalog.rs`
(op catalog), `out_parser.rs`, `opnames.rs`.

See [[Reverse-Engineering-Methodology]] for how to produce the capture.
